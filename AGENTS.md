# Инструкции для агента

## Назначение и порядок работы

Проект — небольшая консольная утилита на Python для замера скорости скачивания
по заданному URL. Объём реализации рассчитан примерно на 1–2 часа.

Перед изменением кода прочитай [контракт](docs/SPEC.md), затем
[индекс тикетов](docs/tasks/README.md) и выбранный тикет с его зависимостями.
Контракт определяет поведение; тикеты определяют порядок и критерии приёмки.
Выполняй текущий запрос пользователя, учитывая зависимости выбранного тикета.

Перед правкой функции найди её вызовы и связанные тесты. Сохраняй чужие изменения.
Закрывай тикет только после выполнения всех критериев и записывай фактические
команды проверок с результатами в раздел «Проверка» его файла.

## Python и инструменты

- Совместимость: Python 3.12+. Рекомендуемая рабочая версия — Python 3.15
  с актуальным исправлением безопасности. Проверяй минимальную и рабочую версии,
  а недоступные проверки отмечай явно.
- Для выполнения и тестов используй стандартную библиотеку: `argparse`,
  `urllib.request`, `time.perf_counter`, `unittest` и `unittest.mock`.
- Единственный сторонний инструмент — Ruff для разработки. Его точную проверенную
  версию зафиксируй в `requirements-dev.txt`; устанавливай инструменты в `.venv`.
- `pyproject.toml` хранит настройки Ruff: `target-version = "py312"`,
  `line-length = 88`, `lint.select = ["E4", "E7", "E9", "F", "I", "UP", "B"]`.
  Это настройки проекта, а не обязательный стандарт Python.

## Стиль кода

- Соблюдай PEP 8: отступы по четыре пробела, `snake_case` для функций и переменных,
  `UPPER_CASE` для констант, явные импорты в начале модуля. Форматирование
  выполняет Ruff: целевая длина строки 88 символов, двойные кавычки, сортировка
  импортов. Порядок групп: стандартная библиотека, сторонние модули, модули проекта.
- Аннотируй параметры и возвращаемые значения функций; используй `list[T]`,
  `tuple[...]`, `T | None`. Типизация дополняет проверку входных данных.
- В именах измеряемых величин указывай единицы: `elapsed_seconds`,
  `downloaded_bytes`, `speed_mib_s`. Значения параметров методики из контракта
  храни в именованных константах модуля.
- Функция выполняет одну законченную операцию. Используй явные условия
  и ранний выход при ошибке; comprehensions — для построения коллекций.
- Пиши короткие docstring по PEP 257 для модуля и публичных функций.
  Комментарии объясняют причину решения. Идентификаторы и docstring — на английском;
  README и тикеты — на русском; сообщения CLI — на английском.

## Архитектура и разделение ответственности

Архитектура — один модуль `speedtest.py` с функциями и один тестовый модуль
`tests/test_speedtest.py`. Разделение ответственности задаётся границами функций:

| Компонент | Ответственность | Граница |
| --- | --- | --- |
| `parse_args` | Разобрать аргументы и проверить URL | Только ввод CLI, без сети и расчётов |
| `download_once` | Полностью прочитать один ответ, измерить время и байты, закрыть ресурс | Возвращает данные одного измерения; HTTP-ответ остаётся внутри функции |
| `measure_downloads` | Последовательно собрать измерения через `download_once` | Управляет порядком вызовов; без формул и вывода |
| `calculate_statistics` | Рассчитать метрики по собранным измерениям | Чистая функция: без сети, часов, чтения аргументов и печати |
| `main` | Связать компоненты, вывести отчёт и обработать ожидаемую ошибку | Владеет stdout/stderr и кодом завершения |

- Направление вызовов: `main` → `parse_args`, `measure_downloads`,
  `calculate_statistics`; `measure_downloads` → `download_once`.
  Загрузчик и расчёты не зависят от CLI.
- Нижние функции возвращают данные или поднимают конкретное исключение;
  `main` преобразует ожидаемые ошибки в сообщения и коды из контракта.
  `print`, `sys.exit` и разбор `sys.argv` остаются на границе CLI.
- Расчёты используют исходные значения. Округление и подписи единиц выполняются
  при выводе. Изменяемое состояние измерений принадлежит текущему вызову функции;
  глобальными остаются только константы.
- Для передачи результатов достаточно простых значений и кортежей.
  `dataclass` допустим, когда имена нескольких полей улучшают читаемость.
- Тесты расчётов проверяют числа, тесты загрузчика подменяют HTTP-ответ и часы,
  тесты CLI проверяют сообщения и коды. Интеграционный тест связывает компоненты
  через локальный сервер. Подмена зависимостей выполняется средствами `unittest.mock`.
- Сохраняй эти границы внутри одного модуля. Отдельный пакет выделяется при появлении
  второго потребителя или самостоятельного сценария; текущей задаче достаточно
  функций без сервисных классов, репозиториев, DI-контейнера и иерархии слоёв.
- Точка входа — `main() -> int` и `raise SystemExit(main())` под проверкой
  `if __name__ == "__main__":`. Импорт модуля не запускает сеть или CLI.

## Корректность

- Проверяй URL до сетевого обращения. Читай тело частями, считай реальные байты,
  освобождай ответ через контекстный менеджер. Сохраняй стандартную проверку TLS.
- Перехватывай конкретные исключения; ошибки программирования должны
  оставаться видимыми.
- Сохраняй последовательность загрузок и точное число измерений из контракта.
  Автоматические повторы и параллельные запросы меняют методику замера.
- Проверяй новое поведение небольшими тестами вместе с реализацией.
  Автотесты работают без внешнего интернета и не сравнивают реальную скорость
  с фиксированным порогом. Для времени используй управляемые показания часов.

## Проверки перед завершением реализации

После появления кода и установки инструментов из корня проекта:

```bash
python -m unittest discover -s tests -v
python -m ruff check .
python -m ruff format --check .
python speedtest.py --help
```

Проверь пример запуска из README. В отчёте разделяй автоматические проверки,
локальный HTTP-прогон и реальный сетевой замер. Публикация завершена только
при наличии доступной ссылки на GitHub и проверки запуска из свежей копии.
